# ADR-0003. Использование монолитной архитектуры для Backend API

**Дата:** 2026-10-06
**Статус:** принято

## Контекст
Необходимо выбрать базовую архитектуру для серверной части приложения. Система должна обрабатывать каталог событий, продажу билетов и возвраты.

## Рассмотренные варианты
1. Микросервисная архитектура: разделение на `CatalogService`, `OrderService`, `PaymentService` с независимыми базами данных.
2. Модульный монолит: единое приложение (Backend API), где модули разделены логически на уровне пакетов, но работают в одном процессе и обращаются к одной БД.

## Решение
Вариант 2 (Модульный монолит).

## Последствия
**Плюсы:** низкий порог входа для разработки, проще управлять транзакциями (например, атомарно менять статусы билета и заказа в рамках одной локальной транзакции БД). Значительно проще развёртывание.
**Минусы:** при резком росте нагрузки (например, старт продаж на финал чемпионата) масштабировать придётся всё приложение целиком, а не только нагруженный сервис оформления заказов.
**Что станет неверным, если решение пересмотреть:** диаграмма контейнеров С4 (L2), диаграмма развёртывания.
